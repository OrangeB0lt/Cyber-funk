# ADR-0006: A small server and PostgreSQL for cloud saves, run with Docker Compose

- **Status:** Accepted (2026-10-31).
- **Amends:** ADR-0001 (the game was a static PWA; it now also ships with a server) and ADR-0002 (`server/` sits beside the six layers).

## Context

Until now v2 was client-only, like v1. The save lived in `localStorage`, so:

- **Progress was tied to one browser.** Switching phones meant copying a `CF2:` export code by hand.
- **The browser could take it away.** iOS Safari deletes a site's storage after seven days without a visit (unless the game is installed to the home screen), and clearing site data wipes it everywhere.
- **The team couldn't see anything.** There was no way to inspect a player's save or roll a broken one back.

The project owner asked for saves in PostgreSQL, the whole application in Docker, and one Compose file to run it all. They also chose:

- anonymous players, with no login
- three save slots plus server-side history
- offline-first play
- development inside Docker as well

## Decision

1. **A small Node server in `server/`.** It uses Fastify 5 for HTTP and Drizzle ORM on `pg`, with SQL migrations generated by drizzle-kit and committed.
   - It serves the cloud-save API under `/api`, and in production also the built game, so everything is same-origin.
   - It sits beside the game's layers, not inside them. It may import only `core` and `app/save/{format,protocol}.ts`, and `src/` never imports it. dependency-cruiser enforces both rules.
2. **One save format, validated on both sides.**
   - The server decodes every upload with the game's own `decodeSave` (Zod) and refuses anything the game couldn't load.
   - The API contract is a set of Zod schemas in `src/app/save/protocol.ts`, parsed by both the client and the server.
   - Saves are stored as `json`, not `jsonb`. jsonb reorders keys, and we want a save that comes back from the cloud to behave byte-for-byte like the local one.
3. **Anonymous players with a player code.**
   - A device gets a random 120-bit secret the first time it uploads. Merely visiting the site creates nothing.
   - The secret is the only credential. It is sent as a bearer token, and the database stores only its SHA-256.
   - Shown to the player as `CFP-XXXX-…`, it links another device to the same saves.
   - There are no cookies, so CSRF can't happen.
4. **Offline-first sync.**
   - The game always saves to the device synchronously (`SaveStorage` stays sync), and `CloudSync` uploads in the background.
   - Each slot carries a revision. A write names the revision it was based on, and a stale base is a conflict (409) that the player settles.
   - A delete leaves a tombstone. Writing over a deletion always wins, so a delete on one device never silently discards progress made on another.
   - The slot of the game being played is never replaced underneath it.
5. **Three slots per player, and the newest 20 checkpoints per slot.** Any checkpoint can be restored; the restore becomes a new revision.
6. **Docker everywhere.**
   - One multi-stage `Dockerfile` has three targets:
     - `dev`: the toolchain
     - `build`
     - `runtime`: Node on Alpine, with the built game, a single esbuild bundle of the server, and the migrations. It has no `node_modules`.
   - `compose.yaml` runs the production stack (app and Postgres 18).
   - `compose.dev.yaml` runs development: Vite with hot reload, the API under `tsx watch`, Postgres, and on-demand `tools` and `e2e` containers.
   - The plain `npm` workflow still works on a host that has Node.

## Consequences

- **The game still works without the server.** `VITE_CLOUD=off` builds a local-only game. The local e2e suite uses it (`.env.test`), and so would any static hosting. Cloud saves are an addition, never a requirement to play.
- **A lost player code is a lost cloud save.** That happens if the browser forgets the code and the player didn't write it down; the device copy is gone too in that case. Accounts with a password or email recovery can be added later on top of player ids, as a separate decision.
- **Two more test suites:**
  - `npm run test:server` runs against a real Postgres: the API rules, plus the browser's sync engine talking to the real server.
  - The `stack` Playwright project drives the Docker stack with two browser contexts as two phones.
  - `npm test` stays database-free and fast.
- **CI gains two jobs:** `server`, with a Postgres service, and `stack`, which runs Compose and the stack e2e.
- **P5's service worker must never cache `/api/*`.** Publishing the game as a static site (the old GitHub Pages idea) now means the local-only build.
- **`@fastify/static` pulls in `glob`, which has a moderate advisory.** It only matters for `wildcard: false`, which we don't use, so `glob` never runs. Upgrade when a fixed release is two weeks old.

## Alternatives considered

- **Express or Hono instead of Fastify.** Hono is smaller. Fastify was chosen for its well-tested plugins (static files, rate limiting) and its in-process `inject`, which the tests use.
- **Prisma or Kysely instead of Drizzle.** Prisma adds a query engine binary and a code generator. Kysely has no schema-to-migration tool. Drizzle keeps the schema in TypeScript and the migrations as plain SQL that can be reviewed.
- **Accounts with passwords from the start.** Rejected for now by the owner: a login screen is friction on a phone, and passwords bring hashing, resets and abuse handling. Player codes give cross-device play without any of it.
- **Server-authoritative saves (no local copy).** Simpler, but progress would be lost on a bad connection, and it conflicts with the plan to be an installable offline app.
- **jsonb with a key-order-independent game.** It would mean auditing every `Object.keys` iteration in the engine for order sensitivity. `json` costs nothing; the summary columns cover querying.
